# Image2 Figure Brief for CARVE-VLA

Updated: 2026-06-12

This document defines the figures that should be generated with Image2 or another high-quality visual model for the current paper:

> CARVE-VLA: A Compute-Adaptive Agentic Runtime for Reliable Long-Horizon VLA Execution

The goal is to create original figures for this version of the paper, not to reuse or visually imitate the previous submitted paper figures archived in `paper/archive/Agentic-VLA-v1-submission/agentic_vla_paper_v1.pdf`.

## 0. Overall Figure Strategy

The paper should use two kinds of figures:

1. **Conceptual method figures**
   - Can be generated by Image2.
   - Should explain the framework and novelty.
   - Should not mention benchmark names such as LIBERO, robosuite, RoboTwin, or IsaacLab unless the figure is specifically an experiment figure.

2. **Result figures**
   - Should be generated from real experiment data using Python/Matplotlib.
   - Do not use Image2 for quantitative plots.
   - Existing task comparison plots can remain data-generated.

Recommended final figure set:

| Figure | Priority | Type | Role |
|---|---:|---|---|
| Fig. 1 | Must | Image2 conceptual framework | Whole-system overview and novelty framing |
| Fig. 2 | Must | Image2 mechanism diagram | Execution-supervision loop and intervention flow |
| Fig. 3 | Should | Image2 module detail | Transition, Memory/Prior, Critic/Retry as three coordinated modules |
| Fig. 4 | Should | Image2 runtime diagram | Realtime-aware VLA call scheduling and low-step inference |
| Fig. 5 | Keep data-generated | Quantitative plot/table | LIBERO task comparison |
| Fig. 6 | Optional data/diagnostic | Quantitative plot/table | Selective refinement or weak-task diagnosis |

If page space is tight, keep Fig. 1 and Fig. 2, then use tables for the rest.

## 1. Global Visual Style

Use this global style for all Image2-generated figures:

```text
Clean academic robotics paper figure, IEEE conference style, white background, flat vector-like design, thin dark outlines, muted colors, high contrast, no decorative gradients, no photorealistic robot, no cartoon character, no benchmark logos, no excessive 3D effects, no clutter. The figure should look original and suitable for a top robotics conference paper. Use minimal short text labels only.
```

Recommended palette:

- Frozen VLA / model: light blue
- Agentic process-control modules: warm amber / orange
- Memory / priors: light green
- Critic / retry / recovery: light red or salmon
- Realtime runtime: lavender / purple
- Robot execution loop / environment: neutral gray or pale green
- Logs / traces / metrics: pale yellow

Important text rule:

- Image models often distort text.
- Prefer short labels only.
- If text quality is poor, ask Image2 for a **no-text version** and add labels manually later in LaTeX, PowerPoint, Figma, or Inkscape.

Do not include:

- Specific benchmark names in framework figures.
- Long paragraphs inside boxes.
- Reused visual layout from the previous submitted Agentic-VLA paper.
- Stock-photo robot arms unless explicitly needed.
- A generic VLM chatbot icon as the central contribution.

## 2. Fig. 1: Main System Overview

### Purpose

This is the most important figure.
It should communicate the paper's core novelty:

> A frozen VLA remains the local action generator, while CARVE-VLA supervises the execution process through transition handling, memory/priors, critic/retry, and compute-adaptive call scheduling.

This figure should not look like a benchmark pipeline.
It should look like a method diagram.

### Suggested placement

Replace the current `fig1_system_overview_agentic_vla_runtime` or the copied old overview figure.

### Required content

The figure should contain five conceptual blocks:

1. **Inputs**
   - RGB observation
   - robot state
   - language instruction

2. **Frozen VLA**
   - central block
   - labeled as "Frozen VLA policy" or "VLA action generator"
   - outputs action chunks

3. **Agentic Process-Control Harness**
   - surrounds or sits above the VLA
   - contains:
     - Transition Agent
     - Scene Priors / Memory
     - Critic / Retry
     - Audit Log

4. **Realtime-Aware Runtime**
   - below or beside the VLA
   - contains:
     - Low-step sampler
     - Call scheduler
     - Action reuse / cache

5. **Robot Execution Loop**
   - receives action chunks
   - returns observations / progress feedback
   - writes runtime traces

## 3. Fig. 2: Execution-Supervision Loop

### Purpose

This figure explains the new problem framing:

> The VLA is not just queried repeatedly. Its rollout is monitored, diagnosed, and conditionally supervised.

It should show the closed-loop sequence over time.

### Suggested placement

Method section, after the failure taxonomy or unified execution loop.

### Required content

Show a timeline or cyclic loop:

1. Observe current state
2. Query frozen VLA for action chunk
3. Execute partial chunk
4. Monitor progress
5. If normal: continue
6. If stalled: activate Transition / Memory / Critic
7. Retry or recover
8. Resume VLA execution
9. Log interventions

### Image2 prompt

```text
Create an academic robotics method figure showing an "execution-supervision loop" for a frozen VLA policy.

Use a horizontal timeline with two paths:

Normal path: Observe state -> Query frozen VLA -> Execute action chunk -> Monitor progress -> Continue.

Failure path: Monitor detects stall or off-nominal progress -> Agentic supervisor activates one of three interventions: Transition, Memory/Prior, or Critic/Retry -> Recovery or prompt repair -> Resume VLA execution -> Log intervention.

Show the frozen VLA as unchanged weights, and show the supervisor as an external runtime layer. Emphasize that intervention happens at inference time, not during training.

Style: clean IEEE robotics paper diagram, white background, flat vector design, muted colors, thin outlines, clear arrows, minimal labels. No benchmark names, no copied style from previous papers, no decorative robot icons.

Aspect ratio: wide single-row or two-row timeline, about 16:6.
```

### Short caption idea

```text
Execution-supervision loop. CARVE-VLA monitors rollout progress around a frozen VLA and triggers transition repair, memory/priors, or critic/retry only when execution evidence suggests that repeated VLA replanning is unlikely to help.
```

### Purpose

This figure replaces the old per-module figures that look too close to the previous submitted paper.
It should be one compact multi-panel figure instead of three separate figures.

### Required content

Three side-by-side panels:

1. **Transition Agent**

2. **Scene Priors / Memory**
   - extracts object / target / approach cues
   - injects compact hints
   - records episodic success cues

3. **Critic / Retry**
   - checks progress consistency
   - clears stale plan
   - triggers retry or recovery

### Image2 prompt

```text

Panel C: "Critic / Retry". Show rollout progress being checked by a critic, stale actions being cleared, and a retry/recovery command returning the system to a useful state.

All three panels should feed into the same frozen VLA policy, but the VLA weights should remain locked or unchanged.

Use a clean top robotics conference style, white background, flat vector illustration, muted colors, thin outlines, no benchmark names, no long text, no photorealistic robot. Make the layout original and different from previous Agentic-VLA figures.

Aspect ratio: wide two-column figure, about 16:7.
```

### Short caption idea

```text
Process-control modules in CARVE-VLA. Transition repair, scene priors/memory, and critic/retry target different observable rollout failures while leaving the VLA backbone frozen.
```

## 5. Fig. 4: Realtime-Aware Runtime and Call Budget

### Purpose

This figure supports the deployment story:

> CARVE-VLA is not only about success rate; it also adapts the VLA call budget to realtime inference pressure.

It should not claim model compression unless we have quantization/pruning/TensorRT experiments.
Use "runtime efficiency" language.

### Required content

Show three mechanisms:

1. **Low-step VLA inference**
   - 1-step / 2-step sampler
   - latency-quality tradeoff

2. **Call scheduler**
   - decides when a full VLA call is needed
   - avoids repeated calls in stalled phases

3. **Delegated recovery / action reuse**
   - external recovery handles stalled segment
   - optional reuse/cache reduces calls

Show output metrics:

- success
- full VLA calls
- latency
- deadline miss / realtime budget

### Image2 prompt

```text
Create an academic system diagram for realtime-aware VLA runtime efficiency.

The diagram should show a frozen VLA policy that is expensive to call. A runtime controller decides among three options: low-step VLA inference, scheduled full VLA call, and delegated recovery or action reuse. The robot execution loop provides progress feedback. The runtime logs four metrics: success, full VLA calls, latency, and realtime deadline budget.

Emphasize that this is runtime-level efficiency and call scheduling, not model compression. Show fewer repeated full VLA calls when the rollout is stalled.

Style: clean IEEE robotics paper figure, white background, flat vector diagram, muted purple for realtime runtime, blue for VLA, orange for agentic recovery, green for robot loop. No benchmark names, no hardware brands, no long text, no photorealistic images.

Aspect ratio: one-column or two-column compatible, about 16:6.
```

### Short caption idea

```text
Realtime-aware runtime. Low-step inference and call scheduling reduce deployment pressure by controlling when expensive full VLA calls are issued, while agentic recovery avoids repeated ineffective replanning during stalled phases.
```
