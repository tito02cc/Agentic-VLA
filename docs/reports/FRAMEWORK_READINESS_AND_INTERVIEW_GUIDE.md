# 具身智能体系统与高效推理：框架说明及汇报指南

更新：2026-09-11。项目：CARVE-VLA；汇报中可使用“Agentic VLA”。
本文描述当前代码与已保存证据，不把规划写成结果。当前优先级是框架完善、面试与汇报，
暂不启动大规模benchmark。本次没有训练模型或新增GPU实验。

完整方法、实验协议、表格、负结果及代码/视频索引统一见

## 1. 先给结论

本项目已经有**可运行的具身智能体研究原型**，不是只有框架图：VLA模型适配、
事件触发VLM、受约束工具调用、恢复执行、新观察核验、状态清理和推理资源管理都有代码；
其中受限恢复链路已有真实RoboDojo运行与视频，输入重放和模型切换也有真实模型记录。

但“主体已搭建”不等于“全部能力均验证”或“机器人成功率已经显著提高”。当前尚不能声称
在RoboDojo实现可靠的开放任务规划、稳定对象身份、长期记忆主动收益或硬实时控制。
这些应作为明确后续目标，不必为了面试先跑完所有benchmark，也不应隐藏证据边界。

## 2. 一分钟项目介绍

> 我研究的是如何把预训练动作模型接入一个可监督、可恢复的具身智能体系统。
> VLA负责从相机、任务指令与机器人状态生成动作，高层VLM负责低频语义检查和恢复建议。
> 中间的Harness维护任务状态、工具权限与预算，把建议转为受约束的执行，动作完成后
> 再用新观察核验结果，而不是让模型直接无限重试。同时，我针对VLM和VLA在单卡部署时
> 的调用与权重搬运开销，搭建了可测量、可回退的推理优化模块，使用固定真实输入检查
> 优化是否改变动作。现在已经有真实仿真、恢复执行视频和模型推理对照；框架能力提升
> 与计算性能提升分开评估，不把更快推理直接等同更高任务成功率。

前期Agentic RAG-VLM承担知识与结构化操作推理基础，当前项目把重心扩展到VLA闭环
执行和模型部署。可以介绍两者的研究承接，但原论文的任务成绩不是当前项目成绩。

## 3. 两条实际实现路径

### 3.1 当前RoboDojo实际执行路径

```text
任务指令 + 相机图像 + 机器人状态
                   |
        RoboDojo/StarVLA策略桥接
                   |
      执行信号Monitor + 语义检查调度
                   |
         低频VLM Critic / Planner
                   |
  能力路由 + 预算 + 原任务约束 + 恢复生命周期
                   |
    Optimize Runtime -> VLA -> 动作块实际执行
                   |
    新相机观察 -> 恢复核验 -> 过程记录/继续或停止
```

当前VLA是官方RoboDojo预训练QwenPI-v3，由StarVLA提供加载与推理；高层使用本地
Qwen3-VL-4B。StarVLA是模型基础设施，不是拿别人的Agent架构替代本项目。
VLM与VLA在当前显存管理路径串行切换，不把通用异步接口说成此路径已经并发推理。

真实入口：`third_party/robodojo_official/XPolicyLab/policy/starVLA/model.py`。
它复用本项目Runtime、Verifier和记忆等模块，但不是通过HTTP/LangGraph派发每一步动作。

### 3.2 可选软件Agent应用路径

```text
外部编码智能体 / 结构化请求
      -> FastAPI认证与输入校验
      -> LangGraph：准入 -> 派发 -> 保存回执
      -> ExternalToolAgentGateway -> CarveAgentSession
      -> CanonicalToolRuntime -> 已绑定的环境/动作执行器
```

代码位于 `agentic_vla/application/`、`external_agent.py`、`session.py`。
这是已实现的可选应用层，本次30项接口/账本测试通过。**本轮RoboDojo视频不证明
这条HTTP服务链已经整体部署到机器人**；应用层测试使用测试绑定，不伪称真实控制实验。
LangGraph在此管理单次工具请求，不是一个自主产生全任务计划的模型。

## 4. Agentic Harness各部分如何工作

| 部分 | 输入与输出 | 为什么需要 | 当前边界 |
|---|---|---|---|
| ExecutionRiskMonitor | 状态响应、动作变化/年龄等执行信号 -> 风险事件 | 低成本发现值得复查的情况 | 程序化监测，不理解“碗是否叠好”；阈值相关性不等于故障真值 |
| VLM Critic | 当前图像、任务、预期状态 -> confirmed/contradicted/inconclusive | 给事件提供语义解释 | 模型可能错，格式合法不代表判断正确 |
| VLM Planner | 图像、事件、有限历史 -> 类型化恢复建议 | 在异常时选择下一步意图 | 当前task-only策略不执行未经验证的自由子任务文本 |
| Harness Controller | 建议、权限、预算、执行状态 -> 允许/拒绝/继续/恢复 | 模型建议不能绕过物理执行约束 | 安全边界是软件约束，不是硬件安全认证 |
| 工具边界 | observe/retrieve_memory/vla_act/run_skill/verify/safe_hold/finish | 分离模型推理与有副作用的动作 | 工具目录统一，实际可用技能取决于adapter，不承诺所有模型都有同样技能 |
| 恢复核验 | 动作块完成后的新观察 -> 核验回执 | 请求发出不等于动作完成，动作完成不等于任务恢复 | 当前两次真实核验均未决，没有当作成功技能 |
| Reset/Trace | 回合边界与操作记录 -> 清理/可追踪回执 | 防止跨回合信息污染、重复记账 | 当前36项reset清单；旧实验按当时冻结清单解释 |

### 4.1 为什么Monitor和VLM都要有

Monitor回答“执行信号是否异常，是否值得进一步检查”；VLM回答“当前场景在任务语义上
意味着什么”。Harness是控制权限拥有者，依据两者证据和预算决定能否行动。
不是Monitor冒充智能模型，也不是让VLM每个机器人控制周期都重新推理。

### 4.2 什么是有预算的恢复

最新已运行的例子：VLM检查发现疑似无进展 -> Planner提出建议 -> task-only路由保留
原任务 -> 清掉旧动作块并申请两个恢复计算动作块 -> 等实际执行完 -> 用新图核验。
次数、动作块数和核验次数有界；结果不确定保留未决，不能无休止重复。
这是原任务下的受约束重规划/重试，不等于已经获得新的抓取技能或学会自由分解任务。

### 4.3 本次补上的证据连续性

- 不确定、被拒绝或任务已满足的观察切断旧停滞数值和跨度，不能跨越未知区间累加。
- 过密观察发现数值变化时打断旧计数；“不计作新停滞证据”不等于“忽略进展”。
- 同一步重复检查和倒序检查不调用VLM、不消耗预算、不改写最新检查时间。
- 恢复后清掉恢复前停滞证据，新的失败判断必须从新观察重新积累。
- 调用档期和证据计数分离；本次不更改实验阈值、不自动把调用预算调成4。

这些检查已进入实际桥接方法，新增5项测试先复现失败，再验证修复。不是仅修改示意图。

## 5. 记忆不是一个泛称

| 类型 | 保存什么 | 使用与限制 |
|---|---|---|
| 任务计划账本 | 待完成、执行中、待重试、已确认阶段 | Harness拥有状态，只有验证后推进；最新RoboDojo矩阵未启用在线多阶段计划 |
| 回合过程记忆 | 当前事件、尝试、结果、核验状态 | 为后续判断提供上下文，回合reset隔离；写日志不自动等于经验学习 |
| 观察/参考记忆 | 历史全图、对象裁剪、标签、来源帧与哈希 | 可选只读链路；标签是模型假设，跨帧对象身份仍待提高 |
| 过程技能记忆 | 验证后的动作过程与适用条件 | 有编译、验证与检索接口；当前RoboDojo自然任务主动收益未完成 |
| 请求回执账本 | 请求ID、规范化请求、派发状态、返回结果 | SQLite避免自动重复派发；不是语义记忆，也不能回滚物理世界 |

代码入口：`agentic_vla/toolchain/planning.py`、`object_memory.py`、`memory.py`、
`reference_observer.py`，以及 `agentic_vla/application/control_plane.py`。

## 6. Optimize Runtime到底优化什么

不是一个宣称“适配所有VLA且无损加速”的黑盒，而是**统一接口、后端适配、测量及质量门控**。

| 层次 | 实现内容 | 已有证据或限制 |
|---|---|---|
| 模型适配与保真 | 固定观测/随机性/动作区间，对比原始与包装路径 | PI-v3真实12个payload，flow4下执行前缀16步全部逐位一致；范围外不作保证 |
| 模型推理后端 | 编译、静态无效相机跳过、量化接口、flow步数配置 | 这些优化各有适用条件；PI0.5历史成绩不能套给PI-v3 |
| 单卡资源调度 | VLA卸载 -> VLM生成 -> VLA恢复；可选冻结权重CPU副本 | 当前PI-v3路径真实测过；主机内存换少量重复回拷，并非降低权重精度 |
| 调用链节流 | 低频检查、调用预算、有效期与事件去重 | 避免把昂贵VLM放入每步控制；当前仍是串行阻塞调用，不声称硬实时 |
| 可观测与准入 | 输入/动作/配置摘要、分项计时、回退条件 | 加速但任务质量下降的配置不能自动成为默认部署方案 |

### 6.1 当前最清晰的优化证据

1. **包装保真**：12个真实输入，同模型、同随机种子、相同flow4，执行前缀16步
   12/12逐位一致。包装器开销中位数2.529 ms，是同一次调用内总时长减模型调用时长。
2. **VLM切换保真**：6个真实输入，两种驻留模式、正反顺序、两次切换后状态，
   已保存报告中动作逐位一致。它是有限输入检验，不是全输入数学证明。
3. **完整语义调用成本**：正序中位数约16.93秒降到5.08秒，反序约16.28秒降到5.27秒。
   每模式3次热VLM调用，实际输出36token；下降约67.6%--70.0%，不是整回合加速。
   主要来自减少冻结权重GPU到CPU回拷，生成本身没有稳定变快；CPU副本约17.712GiB。
4. **不准入的优化**：flow2在12个相同输入上改变动作，且现有stack_bowls开发对照
   没有保持任务效果。因此当前不把减少flow步数作为该任务默认方案。

来源：
- `artifacts/robodojo/native_trace_b0_20260911/replay_report.json`
- `artifacts/robodojo/vlm_switch_residency_20260911/vlm_switch_report.json`
- `artifacts/robodojo/vlm_switch_residency_20260911/vlm_switch_report_reversed.json`

“轻量化”与“高效推理”也要区分：CPU副本驻留不是量化，甚至增加主机内存。
量化/编译有历史后端和实验入口，但当前PI-v3结果不能标为INT4模型结果。

## 7. Kiro阶段哪些保留，哪些纠正

保留：原生请求trace、真实payload捕获/重放、VLM切换分项测量、语义跨度与周期档期修复，
以及离线阈值/预算可达性分析。已有有效工程并不因为换执行助手而推倒重来。

纠正以下过强表述：

- **RGB根因仍是推断。** 已有证据说明观察存在小幅像素差异，同输入模型动作可复现，
  这与渲染数值非确定性相符；还没有单独控制渲染器/预处理的实验，不宜说全部原因已排除。
- **像素不同不意味着不能做benchmark或配对设计。** 固定任务/布局的分块比较仍可做，
  需要重复、平衡条件顺序、记录随机性并估计方差。不能从单一同布局结局断言因果救回；
  也不要求把官方evaluator改到像素逐位确定才能评估总体效果。
- **离线可达31/31不等于挽救31/31。** 可达性是假设语义值一直不变时的机会估计，
  数据又参与阈值选择，只能作开发校准。未用独立数据证明泛化，不自动修改部署默认值。
- **跨度策略不是旧策略等价改写。** 相隔160步的两次读数只覆盖160步；要求320步
  意味着至少第三次名义检查，是有意更严格的策略，会改变触发机会。

### 面试高频问题

**你做的是Agent，还是几条规则？**
高层VLM提供语义判断与结构化建议；规则负责权限、时序、预算和工具安全边界。
有模型不意味着把全部控制交给模型，规则也不能替代模型对图像的理解。

**为什么不直接微调VLA？**
这里解决的是执行组织、恢复、可观测和部署问题，可与微调互补；不是证明微调不需要。
当前动作模型技能边界客观存在，task-only不能靠提示词获得任意新动作。

**你用过LangChain/LangGraph吗？**
本项目有LangGraph工具请求流程、FastAPI接口和SQLite回执账本。能展示实际代码和
30项测试，但不能说RoboDojo当前由LangGraph完整自主调度，也不把框架库本身说成创新。

**记忆带来了多少提升？**
先限定benchmark和实验版本。当前RoboDojo参考记忆与过程记录已实现，长期主动收益
还没有确认；其他历史平台的结果需按独立来源介绍，不能挪用。

**能保证实时吗？**
不能保证硬实时。当前工作证明一些推理/切换成本可以降低，并对输出做有限验证；
低频VLM仍需秒级。真实机器人还需控制时钟、通信、动作队列、过期处理与硬件约束验证。

### 可用于简历的事实版描述

> 构建面向VLM/VLA的具身智能体执行框架，集成事件触发语义检查、受约束工具调用、
> 过程记忆、有预算恢复与动作后核验，并在RoboDojo真实仿真中打通执行链路。
> 设计模型适配与推理保真检查、单卡VLM/VLA资源切换和冻结权重CPU副本管理；
> 在6个真实观测的部署开发对照中，完整语义调用中位耗时由约16.9秒降至5.1秒，
> 已测切换前后VLA动作保持一致。实现可选LangGraph/FastAPI工具服务及幂等请求回执。

这里的“幂等”是请求处理防重复；物理世界和数据库不能原子提交，不是物理动作exactly-once。
